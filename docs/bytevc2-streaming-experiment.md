# ByteVC2 边转换边播放实验

## 目标

减少只有 ByteVC2 片源的分集首次起播时，等待整集转换完成的时间。现有播放器在下载整集并转换成普通 MP4 后才响应视频请求，因此能够使用现有的 HTTP Range 和进度拖动。

## 本地实验

使用 issue #70 中《全球死考：刚下刑场你让我去考试二季》第 6 集（46 秒，1080p）的加密片源，先下载到本机，再使用项目构建的 FFmpeg 解密并输出分片 MP4，H.264 编码参数为 `ultrafast`、`crf 25`，关键帧间隔设为 30 帧。一次本机实验中：

- 输入约 2.1 MB；第一个 `moof` 标识约在启动转换后 0.26 秒出现；该测量不保证完整分片已写出。
- 整集转换约 4.9 秒完成。
- 这是本地文件实验：0.26 秒是首个分片标识出现的时间，不是用户看到画面的起播时间，也不包括取址、下载、浏览器缓冲和其他设备性能差异。

另外使用项目所用版本的 Electron，将转换出的分片 MP4 作为无固定长度的 HTTP 响应逐步送入普通 `<video>` 元素。浏览器能够进入播放状态，但在数据尚未全部到达时报告的时长只有约 8.36 秒；尝试跳到 30 秒也未正确到达目标。因此不能直接把当前转码输出改成流式响应，否则进度条和跳转行为会出错。

## 后续实现方向

可以研究使用 Media Source Extensions 逐步追加分片，并从片源模型提供完整时长。对于跳转到尚未转换的位置，需要明确等待策略或从目标位置重新转换；切集、重复请求、资源限制、转码错误和缓存生命周期也需要覆盖。完整方案应在真实 Electron 播放器中验证首次画面、音画同步、进度拖动及切集取消，并在 Windows 和 macOS 上验证。

这次实验没有修改现有播放路径，也没有验证边下载边解密输入；实际片源还可能有不同的 MP4 元数据布局。不能仅凭本实验认为所有 ByteVC2 片源都能流式起播或按需跳转。
